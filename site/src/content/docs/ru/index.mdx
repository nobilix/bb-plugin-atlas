Этот сайт объясняет, как устроены плагины bb, и описывает каждую поверхность, которую может занять плагин. **bb** ([getbb.app](https://getbb.app)) — открытая «agentic IDE that builds itself». Она работает как сервер на Node с SQLite в роли источника истины, host daemon на каждой машине-исполнителе, клиентское приложение (web, Electron, mobile) и CLI `bb`. Почти всё, что видно в её интерфейсе, и почти всё, что делает её агент, — плагины на одном публичном SDK, и этот SDK — предмет сайта.

## Порядок чтения

Первые четыре страницы читайте по порядку. Каждая опирается на предыдущую: от bb в целом до кода одного плагина.

1. [Как устроен bb](/ru/concepts/) — три процесса и объекты, которыми bb в них управляет.
2. [Как устроен плагин](/ru/architecture/) — три точки входа, как они общаются, где живёт состояние и что делает reload.
3. [Первый плагин](/ru/start/) — сгенерировать скаффолд плагина, установить его, пользоваться им из трёх мест и изменить его.
4. [Выбор поверхности](/ru/choose/) — от идеи к подходящей поверхности и first-party плагину, который стоит прочитать.

Дальше, пока пишете плагин, держите открытым справочник. Он генерируется из закреплённого релиза bb, поэтому страница либо совпадает с выпущенным кодом, либо ломает сборку:

- **[Поверхности](/ru/surfaces/)** — все места, где плагин может появиться или действовать.
- **[Слоты фронтенда](/ru/frontend/)** — точки регистрации, через которые app entry добирается до поверхностей.
- **[Namespace'ы бэкенда](/ru/backend/)** — члены plugin API, которые получает server entry.
- **[Макет UI-зон](/ru/map/)** — те же поверхности, пронумерованные прямо на настоящем окне.

## Как это читать

У каждого символа на этом сайте стоит один из двух статусных чипов, и только у этих двух есть цветная точка:

- `stable`, изумрудный: имя без префикса, и ломающее изменение потребует major-версии.
- `experimental_`, кобальтовый: префикс входит в само имя, а `docs/api_to_audit.md` перечисляет, что нужно проверить, прежде чем префикс снимут.

Если у карточки часть членов стабильна, а часть с префиксом, на ней стоят оба чипа. Обычный тег без точки — подпись, например имя члена, вид слота или роль поверхности; о стабильности он ничего не говорит.

Каждое имя, путь и число ведёт в GitHub на закреплённый коммит, с точной строкой, если она известна. Ссылки генерируются из `data/symbols.json` и никогда не набираются руками. Идентификаторы, пути, команды и UI-строки самого bb приведены ровно так, как их пишет репозиторий. Там, где исследование не смогло подтвердить факт, в тексте стоит **не проверено**, а не догадка.

## Кнопки брифа для агента: что попадает в буфер обмена

На каждой карточке поверхности, слота, namespace'а и продвинутой точки есть три действия. Каждое копирует готовый контекст для агента, который будет писать плагин.

| Кнопка | Что кладёт в буфер обмена | Куда вставлять |
|---|---|---|
| **Бриф для агента** | Markdown-бриф: что это за возможность, в какой точке входа она живёт, точный вызов регистрации, тип пропсов, вид слота, стабильность, символы SDK с путями и строками, какой first-party плагин читать, правила, на которых спотыкаются авторы, и критерии готовности | любой агент в терминале (Claude Code, Codex, Cursor): вставьте бриф первым сообщением задачи |
| **…как упоминание bb** | Ровно тот формат, который даёт встроенный Plugin Guide: `text/plain` с `Build a plugin that uses @<Title>` плюс `text/html` с `data-prompt-mention`. В композере bb это превращается в настоящее упоминание поверхности | композер bb, если включён плагин `plugin-api-docs`; иначе вставится просто текст |
| **Добавить в набор** | Складывает поверхности в набор; панель внизу справа копирует **один** бриф на несколько возможностей: общий скаффолд, архитектура, по блоку на возможность, объединённые правила и чек-лист | плагин, который делает несколько вещей сразу: один запрос вместо трёх |

Набор переживает переходы между страницами и перезагрузку (`localStorage`). Ссылки «Открыть в bb», включая ссылку на встроенный Plugin Guide, ведут на bb, запущенный на этой машине (`http://localhost:38886`).
