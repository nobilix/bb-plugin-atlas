bb состоит из трёх видов процессов: сервера, который хранит всё состояние, окна приложения, где вы работаете, и демона хоста на каждой машине, где агент выполняет задачи. Плагин добавляет код в один или несколько таких процессов. Здесь описаны сами процессы и сущности, которыми управляет bb, а на странице [Как работает плагин](/ru/architecture/) показано, где именно среди них выполняется код плагина.

## Три процесса

Сервер — это процесс Node с базой SQLite в роли единственного источника истины. Он хранит все проекты, треды, настройки и установленные плагины, отдаёт HTTP API и один WebSocket, а по умолчанию слушает `127.0.0.1`. Любая другая часть bb обращается к состоянию только через сервер.

Окно приложения — клиент сервера: веб-клиент, десктопное приложение или мобильный клиент. Оно запрашивает данные у сервера по HTTP и получает изменения пушами через WebSocket. CLI `bb` — такой же клиент сервера. Агент тоже работает как клиент: он обращается к bb через CLI, а также через инструменты и скиллы, переданные ему bb. Когда агент выполняет `bb hello add`, команда идёт ровно по тому же пути, что и введённая человеком.

Демон хоста работает на каждой машине, исполняющей задачи, включая машину самого сервера. Он запускает процесс агента (bb называет его провайдером агента), держит рабочие каталоги, в которых работают треды, и поддерживает сессию WebSocket с сервером. Машина, созданная провайдером машин, запускает собственный установленный демон, который регистрируется на сервере.

## Чем управляет bb

**Проект** группирует работу вокруг репозитория и содержит его `gitRemoteUrl`. Если задача выполняется вне проекта, под неё всё равно используется проект: личный, с `kind: "personal"`.

**Тред** — единица работы. Он содержит одну беседу с провайдером агента и порождает поток событий только на добавление, который окно приложения отображает как таймлайн. **Ход** — один обмен репликами внутри треда: от отправленного пользователем сообщения до конца ответа агента. Стандартный тред выполняет работу сам; тред-менеджер координирует другие треды.

**Окружение** — место, где выполняется тред: рабочий каталог, привязанный к одному хосту. Неуправляемое окружение указывает на уже существующий каталог; управляемое окружение (например, git worktree) создаётся под тред и удаляется, когда его больше не использует ни один неархивированный тред.

**Хост** — долгоживущий идентификатор демона конкретной машины. Машина самого сервера — это `primaryHostId`. **Машина** — то, что подготавливает провайдер машин; как только её демон регистрируется, она становится видна как хост.

Эти сущности составляют словарь API плагинов. Провайдер окружений готовит рабочий каталог на хосте, событие жизненного цикла треда сообщает о завершившемся или упавшем с ошибкой ходе, а панель в окне приложения узнаёт текущий проект и тред через `useBbContext()`.

## Собственные функции bb — тоже плагины

Почти всё, что видно в окне приложения, и почти всё, что умеет делать агент, устроено как плагин на том же публичном SDK, который доступен сторонним плагинам. Провайдеры агентов для Claude Code, Codex, Pi и агентов ACP — это плагины; окружения git worktree, вкладка Diff и кнопка Commit, композер, отслеживание задач, интеграция с GitHub и вопросы с вариантами ответов, которые агент задаёт в треде, — тоже плагины. В bb входит 48 плагинов из поставки bb и 8 плагинов-примеров, перечисленных в [каталоге](/ru/plugins/).

В проектных документах репозитория зафиксировано правило: ядро отвечает за минимум, а «every special case is a public primitive or is deleted». Ядро «never branches on a provider id».
{/* permalink: docs/provider-plugin-api.md */}

Для автора плагина отсюда следуют два вывода. Любая функция, которую вы видите в bb, доказывает, что плагин может делать то же самое через API, который вы можете прочитать. А быстрее всего освоить API можно по плагинам из поставки bb, где он уже используется: страница [Выбор поверхности](/ru/choose/) сопоставляет типичные задачи с такими плагинами.
