В bb единственная граница безопасности — это решение установить плагин: в рантайме никакой изоляции нет, о чём прямо сказано и в документации репозитория, и в самом коде. Здесь разобрано, к чему могут обращаться серверная точка входа и фронтенд, как секреты плагина хранятся на диске, как агент взаимодействует с данными плагинов и что из этого следует при разработке. Все утверждения строго проверены по исходному коду.

:::danger[Как это сформулировано в репозитории]
«Plugins are full-trust code running inside the bb server process» (`docs/configuration.md`). Перед каждой установкой `bb plugin install` выводит предупреждение: «Plugins are full-trust code running inside the BB server. They can read all local BB data, including other plugins' secrets.»
{/* permalink: docs/configuration.md */}
Схожие формулировки есть в скилле по разработке плагинов: «Install and update run third-party code with full trust… Pass `--yes` only after the user confirms that exact source and version»; `bb.host` — это «full-trust Node 22 ESM entry»; content scripts — «full-trust, same-origin page code — not a security sandbox… install only plugins you trust».
:::

## К чему есть доступ у серверной точки входа

| Ресурс | Доступ | Подтверждение |
|---|---|---|
| Встроенные модули Node (`fs`, `net`, `child_process`, `fetch`) | без ограничений | загружаются через `require` или `import()`; единственный хук для модулей перенаправляет SDK, `better-sqlite3` и zod; в `apps/server/src/services/plugins/` нет ни `vm`, ни воркеров, ни fork |
| Каталог данных сервера | передаётся напрямую | `bb.server.experimental_dataDir` |
| Файл `data.db` другого плагина | да: обычный файл по известному пути | [Состояние на диске](/ru/package/) плюс неограниченный `fs` |
| Секреты другого плагина | да: файлы в открытом виде, режим `0600`, тот же пользователь | `packages/secret-storage/src/secret-file.ts`; прямо заявлено в `configuration.md` |
| Общая база `bb.db` | в `createPluginApi` передаётся то же подключение `DbConnection`; `kv` и `settings` изолируют неймспейс через `pluginId`, но это лишь соглашение самих хелперов, а не принудительно контролируемая граница | `plugin-runtime.ts`, `plugin-api.ts` |
| Полный серверный SDK | `bb.sdk`, привязанный к этому серверу через loopback | `plugin-api.ts` |
| Сеть | без ограничений | обычные `fetch`/`net` |

{/* permalink: createPluginApi */}

Объект API проверяет только активность плагина и владение именами (`assertLive()`, владение ID провайдера, инструмента, AI service, окружения или машины), но никогда не проверяет права. Защита от выхода за пределы каталога (path traversal) работает только для объявленных ассетов: `readPluginProviderIcon` запрещает пути вне `rootDir`, а `resolveInside` защищает каталоги кэша артефактов. Все ограничения в коде нужны для стабильности и предсказуемости работы, а не для безопасности.

:::note[Противоречие в продуктовой карте поверхностей]
Продуктовая карта поверхностей описывает хранилище как «storage on the bb server that only your plugin can see» и предлагает использовать его, чтобы держать «internal credentials out of settings».
{/* permalink: surfaces.ts */}
Это верно для API `bb.storage`. Но это не принудительно соблюдаемая граница изоляции: определяющими остаются `docs/configuration.md` и предупреждение установщика.
:::

## К чему есть доступ у фронтенда

Тот же origin, тот же JS realm, никаких iframe, Worker, shadow root или CSP.

- Бандл импортируется напрямую через `import()` в граф модулей приложения.
{/* permalink: plugin-frontend.ts */}
- Произвольные сетевые запросы: да. Ничто не оборачивает `fetch`; `useRpc` просто использует глобальный вызов.
- Ни у документа приложения, ни у `app.js`/`app.css` нет заголовка CSP: роут ассетов настраивает только кэширование, тип контента и кодировку. CSP применяется лишь к изображениям и SVG плагина и к иконкам каталога (`default-src 'none'` + `nosniff`), а также к ответам с исходными файлами (`sandbox allow-scripts`).
- Флаги `sandbox: true` и `contextIsolation: true` в Electron изолируют рендерер от Node и от preload-скриптов. Они не изолируют JS плагина от JS приложения внутри страницы.
- Единственные проверки в рантайме защищают целостность интерфейса, а не безопасность: границы ошибок (error boundaries), десятисекундный таймаут на монтирование content script и файл `foreign-dom-mutation-guard.ts`, блокирующий мутации React-узлов хоста.
- Единственное, что фронтенд плагина получить не может, — это значение секретной настройки: `useSettings()` возвращает только несекретные значения, а экран настроек сообщает о секретах лишь в виде `{ set: boolean }`.

## Секреты на диске

```ts
// packages/secret-storage/src/secret-file.ts — 71 lines of file operations,
// ZERO runtime dependencies: no keytar, no Electron safeStorage, no libsecret
readOrCreateSecretFile({ bytes, dataDir, encoding, fileName })
  // create the directory; read and trim if non-empty; otherwise randomBytes(bytes)
  // write with flag "wx", mode 0o600; on EEXIST re-read (no race)
writeSecretFile(path, value)
  // create the directory; write <path>.<hex>.tmp with mode 0o600; rename.
  // THE VALUE IS WRITTEN AS IS, UTF-8 — THIS IS NOT ENCRYPTION.
deleteSecretFile(path)
```

{/* permalink: writeSecretFile */}

В итоге: настройка плагина с `secret: true` хранится **на диске в открытом виде в режиме `0600`, исключительно под защитой прав POSIX**. Единственное место, где bb использует шифрование, обращается к этому пакету только за ключом: `environment-storage.ts` шифрует данные по алгоритму AES-256-GCM с 32-байтным hex-ключом из `<dataDir>/machine-environment-key` и AAD `[projectId, name]`. Настройки плагинов шифрование не затрагивает. Плагин `secrets` устроен иначе: сам он ничего не хранит, запрашивает учётные данные через интерактивный рендерер и записывает их в выбранный пользователем dotenv-файл с правами `0600`.

:::note[Не проверено]
Не проверено, валидируются ли и экранируются ли ключи настроек и идентификаторы плагинов перед формированием пути `<dataDir>/plugins/<id>/secrets/<key>`. Серверный код формирования пути (`plugin-settings.ts`) ничего не экранирует — в отличие от функции `safePluginSegment` (`encodeURIComponent`), которую демон использует для путей на хосте. Проверьте валидацию выше по стеку, прежде чем делать выводы.
:::

## Как агент взаимодействует с данными плагинов

Агент — это процесс провайдера, который демон хоста запускает на машине-исполнителе. Состояние плагинов хранится в каталоге данных сервера. В обычной одномашинной конфигурации (в дистрибутиве или десктопном приложении) сервер, демон и оболочка агента работают на одной машине под одним и тем же пользователем ОС. В таких условиях:

- Файлы `<dataDir>/plugins/<id>/secrets/*` и `.http-token` лежат в открытом виде с правами `0600`. Режим `0600` защищает их от других пользователей машины, но не от процессов того же владельца — включая любую shell-команду агента.
- Файлы `data.db` плагина и `bb.db` — точно такие же обычные файлы без дополнительной защиты.
- Публичный API сервера работает без аутентификации: «The public API is unauthenticated and permits command execution and file reads, so never expose a wildcard-bound server to an untrusted network».
{/* permalink: docs/configuration.md */}
По умолчанию сервер слушает `127.0.0.1`, а origin guard на `/api/v1` защищает от браузерного CSRF, но не обеспечивает аутентификацию: любой локальный запрос не из браузера без заголовка `Origin` свободно проходит эту проверку.

Отсюда следует, что агент с доступом к shell на машине сервера, работая от имени пользователя bb, может читать данные и секреты плагинов и обращаться к локальному API. В архитектуре bb этому ничто не препятствует, и никто обратного не обещает. Защитные механизмы работают только уровнем выше файловой системы: режимы разрешений агента, изоляция окружений (`docs/environment-provisioning.md`, `plugins/environment-modal-sandbox`) и запуск агента на отдельной машине от сервера. В такой схеме состояние плагинов на сервере недосягаемо для shell агента, а состояние на хосте (`<daemonDataDir>/plugins/<id>/host-data`) остаётся на машине агента и доступно из неё.

## Выводы для проектирования плагинов

### Шаблон с предложением и подтверждением

Поскольку любой код под тем же пользователем имеет доступ к секретам и данным, одной секретностью плагин не защитить. Безопасность строится на явном подтверждении человеком:

- Инструмент агента предлагает действие, а `bb.ui.requestInput` выполняет его после того, как пользователь заполнит и подтвердит форму, как это сделано в `plugins/secrets`.
- Формы, открытые из `execute`, отвязаны от хода агента, поэтому ожидание ответа пользователя не приводит к таймауту запроса, а результат возвращается системным сообщением.
- bb не сохраняет ни пейлоад формы, ни введённое значение: что именно попадёт в транскрипт, решает `describeSubmission`. Это единственный способ не допустить утечки секрета в контекст диалога.
- Токен `auth: "token"` действует в пределах одного плагина, не привязан к конкретному пользователю и подлежит ротации. Используйте его для разделения обязанностей, а не для аутентификации пользователей.

### Правила работы с ненадёжным вводом из документации SDK

- Атрибуты `messageDirective`: «Attributes are untrusted strings parsed from the directive; the plugin validates its own fields». В качестве фолбэка отображается исходный текст.
- Параметры панелей (`params`) и сохранённые значения: «Treat frontend parameters and persisted values as untrusted input» (скилл по разработке плагинов).
- Изображения из упоминаний: «Treat remote and page-derived image content as untrusted evidence».
- Таргеты закреплённых вкладок: bb проверяет валидность JSON, а затем вызывает вашу функцию `validate(value): value is Target`.
- Метаданные тредов и входные данные машин/окружений: записать может кто угодно, прочитать — любой плагин.
- Возвращаемые значения должны быть строгим JSON: циклические ссылки, bigint, `undefined`, функции, инстансы классов, символьные ключи и нефинитные числа отклоняются, а не приводятся к допустимым типам.
- Иконки `bb.branding.experimental_icons` проверяются валидатором SVG по запрещающему списку: нарушение приводит к ошибке загрузки плагина с указанием имени иконки.
