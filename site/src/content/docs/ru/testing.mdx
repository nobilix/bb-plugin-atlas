Здесь описаны четыре тестовых стенда, работающих без запущенного bb: `createFakePluginHost` (бэкенд), `renderSlot` + `loadPluginApp` (фронтенд), `createFakeSdk` и `experimental_createHostEntryHarness` (хостовая точка входа). Вы узнаете, чем управляет и что отдаёт каждый стенд, а также где заканчивается их достоверность.

## Бэкенд: `createFakePluginHost`

Стенд пригодится в первую очередь авторам серверных точек входа: он даёт настоящий объект `bb` и пульт управления им, применяя те же правила, что и продакшен — вплоть до отказа регистрировать провайдер для плагина без `bb.host` и отказа принимать глиф с неймспейсом, которого не было в манифесте.

```ts
import { createFakePluginHost } from "@get-bb/plugin-sdk/testing";
import plugin from "./server";

const { bb, harness } = createFakePluginHost({
  pluginId: "hello",                              // defaults to "test-plugin"
  settings: { showDone: false },                  // as if saved before this load, secrets included
  sdk: { threads: { list: async () => [] } },     // bb.sdk stubs; extend with harness.sdk.stub(...)
  experimental_hostEntry: true,                   // whether the manifest declares bb.host; default true
});
try {
  await plugin(bb);   // an ordinary call of your factory

  // drive the surfaces "as the host would"
  await expect(harness.behavior.callRpc("todos_add", { title: "Ship it" }))
    .resolves.toMatchObject({ title: "Ship it" });
  const cli = await harness.behavior.runCli(["list"]);
  expect(cli.exitCode).toBe(0);

  // and read back what the plugin did
  expect(harness.registrations.rpcMethods).toContain("todos_add");
  expect(harness.realtimeSignals.at(-1)?.channel).toBe("todos-changed");
  expect(harness.logEntries[0]).toMatchObject({ level: "info", message: "loaded" });
} finally {
  await harness.lifecycle.dispose();   // runs onDispose and clears the temporary storage
}
```

### Что умеет `harness.behavior`

`callRpc(method, input?, { experimental_caller?, signal? }?)` · `experimental_watchRpc(method, read)` · `runCli(argv, ctx?)` · `fetchHttp(...)` · `experimental_openWebSocket(...)` · `runService(name)` · `runSchedule(name)` · `emitThreadEvent(event, payload)` · `callAgentTool(...)` · `resolveAgentConfiguration(context)` · `resolveProviderEnv(...)` / `resolveProviderEnvHealth(...)` · `setSettings(values)` · `submitInteraction(id, value)` / `cancelInteraction(id)` · `experimental_emitHostSignal(...)` / `experimental_emitHostWorkerExit(hostId)`.
{/* permalink: createFakePluginHost */}

`harness.lifecycle` содержит `reload(factory)`, `dispose()` и `install()`, который запускает обработчики `bb.onInstall` ровно так, как это делает bb после чистой установки. Сам объект `harness` наследует методы инспекции, поведения и жизненного цикла, поэтому `harness.callRpc(...)` и `harness.behavior.callRpc(...)` делают одно и то же.

### Что доступно для инспекции

`pluginId` · `logEntries` · `realtimeSignals` · `experimental_rpcInvalidations` · `needsConfigurationMessages` · `recheckCount` · `sdk` (`FakeSdkHarness`) · `registrations` (маршруты, RPC-методы, расписания, сервисы, CLI, инструменты, провайдеры упоминаний и `experimental_publishedRpcMethods` с описаниями и JSON-схемами доступных для обнаружения методов) · `sharedPortDeclarations` · `experimental_hostRpcCalls` · `pendingInteractions`.

Ещё два стенда. `createFakeSdk({ pluginId, overrides })` — отдельный дублёр `bb.sdk`, записывающий вызовы: они фиксируются после серверной нормализации, а вызов без заглушки выбрасывает ошибку с точным путём, который нужно заглушить.
{/* permalink: createFakeSdk */}
`experimental_createHostEntryHarness(entry, options?)` из `@get-bb/plugin-sdk/testing/host` запускает хостовую точку входа внутри процесса через те же границы, что использует демон (валидация, JSON-транспорт, отмена, жизненный цикл и лимит на размер ответа), и открывает доступ к `experimental_call`, `experimental_getSignals()`, `experimental_getRetainedWorkerLeaseCount()`, `experimental_lifecycleSignal` и `experimental_dispose()`. Падения процессов остаются зоной ответственности интеграционных тестов демона.
{/* permalink: experimental_createHostEntryHarness */}

## Фронтенд: `loadPluginApp` и `renderSlot`

```tsx
// plugins/tasks/app.test.tsx (abridged) — a nav panel badge refreshed by RPC invalidation
// @vitest-environment jsdom
import { cleanup, waitFor } from "@testing-library/react";
import { loadPluginApp, renderSlot } from "@get-bb/plugin-sdk/testing/app";
import { projectTasksChangedTags, taskChangedTags } from "./shared/tags";

const app = await loadPluginApp(() => import("./app"));   // THE THUNK FORM ONLY!
const useBadge = app.navPanels[0]!.experimental_useBadge!;
function Badge() {
  const badge = useBadge();
  return badge === null ? null : <span>{badge.count ?? "dot"}|{badge.label}</span>;
}
afterEach(cleanup);

const slot = renderSlot({ component: Badge }, {}, {
  rpc: { sidebarOpenTaskCount: () => ({ openTaskCount }) },
});
expect(await slot.findByText("12|12 open tasks")).toBeDefined();
openTaskCount = 13;
await slot.behavior.experimental_invalidateRpc(taskChangedTags({ id: "…", projectId: "…" }));
await waitFor(() => expect(slot.getByText("13|13 open tasks")).toBeDefined());
openTaskCount = 7;
await slot.behavior.experimental_invalidateRpc(projectTasksChangedTags("…"));
await waitFor(() => expect(slot.getByText("7|7 open tasks")).toBeDefined());
expect(slot.inspection.rpcCalls.filter(({ method }) => method === "sidebarOpenTaskCount"))
  .toHaveLength(3);
```

### Три шага работы с фронтенд-стендом

- `installTestPluginRuntime()` заполняет `globalThis.__bbPluginRuntime.pluginSdkApp`. Вызовите её до вычисления `app.tsx`, так как этот модуль связывается с рантаймом при импорте.
- `loadPluginApp(source)` инициализирует рантайм, резолвит определение, проверяет маркер `__bbPluginApp` и прогоняет тот же валидирующий сборщик, что и хост, с теми же текстами ошибок. Передайте функцию `() => import("./app")`, чтобы модуль плагина вычислялся строго после установщика.
- `renderSlot(registration, props, options?)` принимает `{ component, experimental_usePageTitle? }`, поэтому сюда подходит любой компонент, включая небольшую обёртку вокруг хука регистрации — так в тесте плагина Tasks обёрнут `navPanels[0].experimental_useBadge`.

`RenderSlotOptions` принимает `rpc` (входные данные и результаты сериализуются строго в JSON, как и по сети; метод без обработчика отклоняется с «no rpc handler for …»), `settings`, `context`, `realtimeConnectionState`, `composer`, `sidebarThreads`, `providers`, `codeTheme`, `branchesState`, `checkoutState`, `sdk`, `experimental_panel`, `experimental_panelTabs`, `experimental_fixedTabTarget`, `openUrl`, `openFilePreview`, `openFileExternally`, `openTerminal` и `servers`; остальные параметры описаны в типе `RenderSlotOptions`.

### Что возвращает стенд

- `behavior`: `experimental_invalidateRpc(tags, pluginId?)` (обновляет совпадающие чтения точно так же, как `bb.rpc.experimental_invalidate`), `emitRealtime` (обёрнут в `act`, а полезная нагрузка проходит через JSON ровно так же, как в `bb.realtime.publish`), `setRealtimeConnectionState`, `setComposerText`, `setComposerScope`.
- `inspection`: `rpcCalls`, `navigateCalls` (дискриминированное объединение по всем восьми методам `BbNavigate`), `experimental_panelCalls`, `sidebarNavigationCalls`, `sdkCalls`, `experimental_clipboardWrites`, `experimental_pageTitle`, `composer` (текст, черновик, область действия, выделение, число вложений, эффекты, блокировки, цитаты, упоминания, фокусы, отправки).
- `lifecycle`: `rerender(ui)`, `unmount()`.
- Для content script есть свой стенд — `mountPluginContentScripts(app, { pluginId, generation?, omitExperimentalThreadRowStatus? })`; последний флаг имитирует старый хост без API статуса строк. Порядок монтирования строго соответствует хосту: если при монтировании возникает исключение, уже смонтированные скрипты размонтируются в обратном порядке, после чего ошибка пробрасывается дальше.

:::caution[Пределы достоверности]
Компоненты хоста в стенде — это заглушки, записывающие свои пропсы в data-атрибуты, а не настоящие движки: `bb-thread-chat`, `bb-markdown`, `bb-new-thread-composer`, `bb-provider-model-picker`, `bb-branch-picker`, `bb-permission-mode-picker`, `bb-source-code`, `bb-diff`.
`useComposerView()` возвращает `layout: "expanded"` и композер, который ничего не выполняет и не отправляет, если только в опции `composer` явно не заданы `layout`, `isRunning` или `isSubmitting`; `experimental_useSidebarThreadSplit` всегда возвращает `isAvailable: true` и `layout: null`; кроме того, у композера в стенде нет пайплайна отправки, поэтому `submit` лишь сохраняет переданные параметры и очищает черновик.
Для мостов предусмотрен отдельный инструментарий: `experimental_runBridgeConformance` + `experimental_captureBridgeJsonRpcOutput().takeMessages`, с рабочими примерами в `examples/plugins/echo-provider/provider-bridge.{conformance,stream,parity}.test.ts`.
:::
