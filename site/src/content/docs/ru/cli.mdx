Здесь собраны команды плагинов в CLI bb, а также описаны типы установки, отслеживание версий, фильтрация по `engines`, откат, маркетплейсы, публикация и расположение бинарника bb в десктопной версии.

## Справочник `bb plugin *`

| Command | Flags | What it does |
|---|---|---|
| `plugin search <query>` | `--json` | поиск по всему каталогу (bundled + `bb-community` + добавленные маркетплейсы); колонка Marketplace указывает источник |
| `plugin list` | `--json` | установленные плагины и их статус, а также сервисы, расписания, замеры времени обработчиков и команды, добавленные в `bb` |
| `plugin source <id>` | `--json` | разрешённый источник и его история: поддиректория, semver-диапазон, префикс тега, разрешённый тег, диапазоны движков, время установки, целостность и история активаций |
| `plugin install <source>` | `--subdirectory` · `--plugin` · `--tag-prefix` · `--yes` · `--no-wait` · `--json` | запись каталога по имени или `<entry>@<marketplace>`, Git-URL, локальный путь, `builtin:<name>`, `git:<url>[@<ref\|semver>]`, `npm:<name>@<version>`; с `--no-wait` запускает установку в фоне и выводит ID задания |
| `plugin install-jobs` | `--json` | установки в очереди или в процессе выполнения, а также завершённые за последние десять минут; задачи выполняются на сервере по очереди и не прерываются при отключении CLI |
| `plugin cancel-install <job-id>` | `--json` | отменить установку из очереди или остановить выполняющуюся, чтобы ничего не установилось, если регистрация плагина ещё не началась |
| `plugin outdated` | `--json` | проверить совместимые обновления; также сообщает о более новых релизах, заблокированных из-за несовместимости |
| `plugin update [id]` | `--all` · `--yes` · `--no-wait` | применить только совместимые кандидаты; требует того же подтверждения полного доверия, что и установка; без TTY и флага `--yes` завершается с ошибкой; ждёт завершения серверного задания, если не передан `--no-wait` |
| `plugin update-jobs [job-id]` | `--json` | фоновые обновления и их результаты (хранятся десять минут); запущенная задача переживает отключение клиента, но не перезапуск сервера |
| `plugin new <name>` | none | создать шаблон плагина в `./bb-plugin-<name>`; принимает `@scope/bb-plugin-<name>` |
| `plugin types [path]` | `--check` | синхронизировать поверхность SDK с запущенным bb: заново зафиксировать devDependency SDK и чисто типовые devDeps шиммированных пакетов; с `--check` ничего не записывает |
| `plugin migrate [path]` | `--yes` | перевести плагин с вендоренной директории `types/` на npm-пакет: закрепить devDependency, убрать path map из tsconfig, удалить вендоренные декларации и переписать импорты `@bb/plugin-sdk`; выводит план и запрашивает подтверждение |
| `plugin build [path]` | none | собрать в `dist/`: серверную часть всегда, клиентскую при наличии `bb.app`, самодостаточный хостовый бандл при наличии `bb.host`; сервер не требуется |
| `plugin dev [path]` | none | режим наблюдения: пересобирает фронтенд (без минификации), хостовый бандл и бандлы моста провайдера, а затем перезагружает плагин при каждом изменении |
| `plugin reload [id]` | `--json` | перезагрузить один плагин или все; завершается с кодом 1, если перезагруженный плагин не запустился |
| `plugin enable` / `disable <id>` | `--json` | включить или отключить плагин (код выгружается из памяти) |
| `plugin config <id> [action] [key] [value]` | `--json` | показать настройки либо выполнить `config <id> set <key> <value>` / `unset <key>`; булевы значения и числа приводятся к объявленным типам |
| `plugin token <id>` | `--rotate` · `--json` | вывести HTTP-токен плагина (для маршрутов с `auth: "token"`) |
| `plugin run <id> [args...]` | `passThroughOptions` | явная форма `bb <command>`, исключающая коллизии имён |
| `plugin logs <id>` | `-n/--lines` (100) · `-f/--follow` | логи плагина (вывод `bb.log`); с флагом follow опрашивает раз в секунду |
| `plugin remove <id>` (alias `uninstall`) | `--json` · hidden `--yes` | удалить плагин вместе с его настройками, секретами и расписаниями; управляемые файлы git/npm удаляются, локальные пути остаются на диске |
| `plugin safe-mode [state]` | `--json` | показать состояние безопасного режима либо переключить его: `on` останавливает все установленные вами плагины, оставляя плагины из поставки bb; `off` перезапускает те, что были включены (завершается с кодом 1, если какой-то плагин не запустился) |
| `plugin prune` | `--dry-run` · `--json` | удалить кэшированные версии плагинов, которые не используются ни одним установленным плагином; не удаляет версию, запущенную установленным плагином, или локальный источник по пути |
| `plugin rpc list [plugin-id]` | `--method` · `--json` | доступные для обнаружения RPC-методы запущенных плагинов |
| `plugin rpc inspect <plugin-id> [method]` | `--json` | описание регистрации и метода, а также JSON Schema для входных и выходных данных |
| `plugin rpc call <plugin-id> <method>` | `--input-file` · `--json` | вызвать метод с валидацией схемы на сервере; без файла передаёт JSON `null` (файл защищает секреты от попадания в argv) |

{/* permalink: apps/cli/src/commands/plugin.ts */}

Смежные команды: `bb marketplace add|list|refresh|remove`; `bb theme list|set|show` (показывает палитры плагинов как `plugin:<plugin-id>:<id>`); `bb settings keyboard` (команды плагинов переназначаются с префиксом `plugin:<plugin-id>/<command-id>`); и `bb diagnostics cli-errors` (счётчики сбойных вызовов `bb`: записывает путь команды и код ошибки, никогда не сохраняя значения аргументов; отключается переменной `BB_CLI_ERROR_LOG=0`).

## Типы установки и отслеживание версий

```bash
bb plugin install ./bb-plugin-notes                            # path
bb plugin install path:. --plugin notes                        # path + a collection entry
bb plugin install npm:bb-plugin-notes@^1.0.0                   # npm: range / dist-tag / exact version
bb plugin install https://github.com/acme/bb-plugin-notes      # bare URL → the default branch
bb plugin install git:https://github.com/acme/x.git@main       # an explicit branch (tracking)
bb plugin install git:https://github.com/acme/x.git@^1.2.0     # semver over vX.Y.Z tags
bb plugin install builtin:<name>                               # a local copy from the application bundle
bb plugin install <entry-id>@<marketplace>                     # a marketplace entry
```

### Отслеживание версий и пиннинг

- npm: если спецификатор не указан, отслеживаются совместимые стабильные релизы; диапазоны и dist-теги отслеживают изменения, точные версии фиксируют их.
- git: если ref не указан, отслеживается ветка по умолчанию; имена веток отслеживают изменения, теги и коммиты фиксируют версию.
- semver-диапазон для git разрешается по тегам `vX.Y.Z` с выбором максимального совпадения; пререлизы исключаются, если они явно не названы в диапазоне. Флаг `--tag-prefix` позволяет отслеживать теги конкретных плагинов в монорепозитории.
- bb сохраняет выбранный тег вместе с его коммитом и отказывается заново разрешать тег, если тот сместился (урок `go.sum`). Исправления публикуют новой версией, а не перестановкой тега.
- Простой спецификатор, похожий на диапазон, разрешается по тегам только тогда, когда ни одна ветка и ни один тег не называются буквально так же; если существует и то и другое, установка завершается ошибкой — тогда нужно явно указать `@semver:<range>` или `@ref:<name>`.

### Поведение сборки для разных типов

- **path**: загружает TypeScript из `bb.server` напрямую без сборки; `bb.app` собирается при установке из уже имеющихся зависимостей. Установка по локальному пути плагина с идентификатором, уже установленным из другого локального каталога, переносит плагин, сохраняя его настройки, секреты и расписания.
- **git**: сначала выполняет `npm install --omit=dev --omit=optional --ignore-scripts`, сохраняя `node_modules` (бандлер не умеет упаковывать файлы данных, читаемые во время выполнения), затем объявленные сборки app/server/host и проверку метаданных. Требуется `git`; npm и Node в PATH не нужны, так как bb поставляет npm с собой.
- **npm**: пакет обязан поставлять готовую и корректную директорию `dist/`: с `app.js` + `app.meta.json`, если объявлен `bb.app`, и хостовым бандлом с метаданными, если объявлен `bb.host`.
- **builtin**: копируется из бандла приложения без обращения к сети.
- Повторная установка уже установленного управляемого плагина отклоняется; используйте `bb plugin update`. Чтобы сменить зафиксированный источник `git:`/`npm:`, плагин придётся удалить через `remove` (с потерей настроек) и поставить заново начисто.

## Фильтрация по engines, откат и маркетплейсы

- При обновлениях выбираются только совместимые кандидаты, удовлетворяющие условиям `engines.bb` и `engines.bbPluginSdk`; более новые несовместимые релизы помечаются как заблокированные и не применяются. Сборки для разработки указывают, что `engines.bb` не проверялся.
- Откат: если активация завершилась неудачей, восстанавливается предыдущий снимок состояния и сохраняется запись о сбое для пользователя.
{/* permalink: plugin-state-snapshot.ts */}
- Плагин, установленный по локальному пути, никогда не нужно удалять ради правок: редактируйте файлы на месте и вызывайте `bb plugin reload <id>` либо `bb plugin install path:<new dir>`; в обоих случаях конфигурация сохраняется.
- Удаление маркетплейса оставляет все установленные из него плагины работать как прямые установки с сохранением исходного намерения и точного разрешения версий, поэтому `outdated` и `update` продолжают работать.
- Маркетплейс — это один файл `marketplace.json` (в git-репозитории он может лежать в поддиректории, указанной через `bb marketplace add --subdirectory`). Он содержит список плагинов с оформлением для каталога и ссылками на npm/git, но никогда не хранит код у себя. Схема строгая: любое неизвестное поле приводит к отклонению всего документа, и bb продолжает использовать последний валидный каталог. Имена `bb-official` и `bb-community` зарезервированы, их нельзя добавить или удалить. Запись в каталоге не задаёт совместимость: секция `engines` считывается из `package.json` самого плагина.
- Перед установкой из любого маркетплейса, кроме `bb-community`, bb находит и показывает фактический источник (включая точный тег релиза и коммит, под который подошёл диапазон), а также маркетплейс и автора записи. Установка завершится ошибкой, если запись в каталоге или разрешённый коммит изменились после подтверждения.
- `bb-official` описывает все плагины из бандла приложения с помощью сгенерированного документа v2, указывающего на локальные пути, и никогда не обращается к сети. `bb-community` перечитывается при старте и каждые два часа по адресу `https://getbb.app/marketplace/v2/marketplace.json` (с одним откатом к v1 при 404; переопределяется переменной `BB_MARKETPLACE_URL`, которая считывается только при запуске). Число установок берётся из файла `stats.json` рядом с курируемым манифестом; bb собирает эти данные через анонимную телеметрию, поэтому они занижены.

## Публикация и выпуск версий

Установка из `path` и `git` собирает плагин на месте. Пакет npm обязан содержать уже собранную и валидную директорию `dist/`: `dist/app.js` + `dist/app.meta.json`, если объявлен `bb.app`, и хостовый бандл со своими метаданными, если объявлен `bb.host`. Управляемая установка проверяет метаданные и отклоняет артефакт, если его `pluginId`/`pluginVersion` не совпадают с манифестом или если `sdkMajor` отличается от текущего.

```bash
# before publishing
bb plugin types          # re-pin the SDK and type-only devDeps to the current bb
bb plugin types --check  # the same in CI: writes nothing, fails on a mismatch
bb plugin build          # dist/server.js (+ app, + host) and their *.meta.json
npm publish              # the package MUST contain dist/ — the scaffold's .gitignore hides it
                         # from git only, but it has to reach the npm package
```

Шаблон плагина генерирует `.gitignore` ровно из двух строк (`dist/` и `node_modules/`) и не добавляет поле `files` в `package.json`. Что именно прописывать в `files` (или в `.npmignore`), чтобы `dist/` попал в тарбол, в репозитории не сказано (**не проверено**); перед публикацией проверьте содержимое пакета командой `npm pack --dry-run`.

### Версионирование и `engines`

- `engines.bb` задаёт диапазон версий приложения; `engines.bbPluginSdk` интерпретируется как нижняя граница, а не верхняя. Шаблон плагина прописывает `>=major.minor` текущего bb и точную версию SDK.
- При обновлениях выбираются только совместимые кандидаты. Более свежий релиз, не проходящий проверку `engines`, отображается в `bb plugin outdated` как заблокированный и не применяется. Управляемая установка дополнительно отклоняет плагин, чей SDK новее хоста или относится к другому major-релизу.
- Исправления нужно публиковать в виде новой версии: bb сохраняет выбранный тег вместе с коммитом и отказывается разрешать тег, если тот сместился.
- Для git-источников semver-диапазон разрешается по тегам вида `vX.Y.Z`; плагины в монорепозитории разделяются флагом `--tag-prefix`.

### Тексты для каталога и публикация в `bb-community`

- Для каталога обязательны два текста: `bb.description` — одно предложение длиной до ~140 символов для карточки в Browse и первого абзаца страницы плагина; `PLUGIN_OVERVIEW.md` рядом с `package.json` — подробное описание в разделах ниже.
- Требования CI к файлу описания: кодировка UTF-8, жёсткое ограничение в 4000 символов (рекомендуется 700–1800); разрешены только заголовки, абзацы, курсив, полужирный шрифт, зачёркивание, инлайн-код, блоки кода, цитаты, списки, разделители и ссылки; никакого сырого HTML, изображений, таблиц, сносок и чек-листов; все ссылки строго абсолютные по https; заголовки только уровня `##`; нельзя начинать с `#` и повторять краткое описание в первом предложении.
- Отправка — это отдельный скилл, `plugins/bb-guide/skills/submit-a-plugin/`: он копирует `PLUGIN_OVERVIEW.md` в репозиторий маркетплейса как `overview/<plugin-id>.md` и указывает его в поле `"overview"`. Попадание в `bb-community` — это релизное решение bb, а не часть процесса автора.
- Собственный маркетплейс — это один файл `marketplace.json`, который подключается командой `bb marketplace add` по URL с https либо из источников `git:` или `path:`. Он не хранит код плагинов, а их установка проходит через тот же пайплайн.

## Бинарник `bb` в десктопной установке

Портативным решением служит переменная окружения `BB_CLI`, содержащая абсолютный путь к бинарнику под управлением демона: «Prefer bare `bb` on PATH. When `BB_CLI` is set, official `bb` entrypoints re-exec to that absolute binary; in a POSIX shell you can also invoke `"$BB_CLI"` directly». Лаунчер выставляет `BB_CLI: join(args.context.daemonBundleDir, "bb")`, а при пакетной установке `daemonBundleDir = <bb-app package root>/host-daemon/dist`.
{/* permalink: launcher.ts */}

Путь вида `bb.app/Contents/Resources/app.asar.unpacked/node_modules/bb-app/host-daemon/dist/bb` буквально в репозитории не встречается. Он выведен из трёх отдельных фактов и потому помечен как **не проверено**; используйте `$BB_CLI`.
