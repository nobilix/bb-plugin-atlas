Провайдер агента позволяет плагину отвечать за самого агента. Он состоит из двух половин в одном артефакте: декларации на сервере и моста на машине. Здесь также разбираются диалекты ACP и режим записи моста. Поверхности [Провайдеры агентов](/ru/surfaces/provider-picker/) и [Мосты провайдеров](/ru/surfaces/provider-bridges/) содержат списки символов SDK для каждой из половин.

| Половина | Импорт | Основные имена |
|---|---|---|
| декларация (сервер) | `@get-bb/plugin-sdk` | `bb.providers.register(declaration)` → `{ dispose() }` · `PluginProviderDeclaration` |
| мост (хост) | `@get-bb/plugin-sdk/provider-bridge` | `experimental_defineProviderBridge` · `PROVIDER_BRIDGE_EXPORT_NAME` · `BRIDGE_REQUEST_METHODS` · `BRIDGE_JSON_RPC_ERRORS` · `PROVIDER_BRIDGE_PROTOCOL_VERSION` · `THREAD_DELTA_GRAMMAR_V2`/`V3` · `runBridgeRequest` · `createBridgeIo` · `addTokenUsage` · `experimental_spawnPortableProcess` · `experimental_killPortableProcess` · `experimental_scanSkillFiles` |
| набор ACP | `…/provider-bridge/acp` | `experimental_acpProviderBridge` · `experimental_acpLaunchSpecSchema` · `experimental_probeAcpAgent` · `experimental_registerAcpDialect` |
| проверка соответствия | `…/provider-bridge/testing` | `experimental_runBridgeConformance` · `experimental_createBridgeJsonRpcTestHarness` · `experimental_captureBridgeJsonRpcOutput` · `experimental_createDeltaAssembler` · `experimental_replayRecording` · `experimental_compareParity` |

```ts
// examples/plugins/echo-provider/src/provider-bridge.ts (abridged) — a minimal bridge
const handlers: Record<string, RequestHandler> = {
  [BRIDGE_REQUEST_METHODS.initialize]: (id, params) => {
    io.sendResult(id, {
      protocolVersion: PROVIDER_BRIDGE_PROTOCOL_VERSION,   // exactly 2
      capabilities: {
        grammarVersions: [THREAD_DELTA_GRAMMAR_V3, THREAD_DELTA_GRAMMAR_V3],
        sessionRestore: true, threadArchive: false, threadRename: false,
        threadGoalClear: false, fork: "none",
        approvalEnforcedBy: "runtime", steerMode: "queue",
      },
    });
  },
  [BRIDGE_REQUEST_METHODS.threadStart]: (id, params) => { /* … io.sendResult(id,
      { providerThreadId, sessionRestorable: true }) … */ },
};
export const experimental_providerBridge = experimental_defineProviderBridge({ handleLine, start });
```

**Транспорт.** JSON-RPC 2.0 с разделением строк по \n через stdin/stdout процесса моста в обоих направлениях; запросы и ответы различаются по наличию `method`, «never on result shape»; у этих двух направлений независимые пространства идентификаторов. Вывод в stdout не по протоколу игнорируется; мост должен сам следить за своим stdout.

**Грамматика.** Ассемблер поддерживает только v3 (`[3, 3]`): мост, диапазон которого не включает 3 (включая мосты, созданные до появления этого поля), отклоняется при запуске с понятной ошибкой. Факт из рукопожатия может только сузить объявленное в декларации, но никогда не расширить.

**Кто чем владеет.** Сервер генерирует `threadId`, провайдер — `providerThreadId`, а ассемблер в демоне — идентификаторы ходов и элементов, так что «a bridge does zero id translation».

**Минимальный корректный ход.** `input.accepted { clientRequestId }` → `turn.open` → дельты элементов → `turn.boundary { status }`. Даже на промпт, который провайдер обрабатывает без какой-либо работы, он обязан выдать пару open+boundary, «or the thread hangs»; правило проверки соответствия `turn/settles-without-activity` это проверяет. После `thread/stop` мост ничего не задерживает: всё, что он ещё должен отправить, прежде всего финальную границу прерванного хода, нужно выдать в канал до ответа.

**recovery.** Типизировано, совпадение по тексту не используется: `sessionArchived`, `authRequired`, `restartRecommended`, `staleTurn`, `rateLimited`. Один полезный груз, два способа доставки: подсказка об отклонённом запросе передаётся в `error.data.recovery`, инициативное уведомление — в виде нотификации `provider/recovery`. «Never send both for one event.»

**Подводные камни.** SDK должен лежать в `dependencies`, а не только в `devDependencies`; приватные пакеты `@bb/*` запрещены; импорт модуля моста не должен ничего запускать (бутстрап демона сам управляет argv, `dataDir`/`tempDir`, фреймингом stdin и сигналами); не генерируйте `providerThreadId` через счётчик внутри процесса; мост, запускающий дочерние процессы, обязан использовать `sanitizeInheritedChildProcessEnv`, а вместо `spawn` для исполняемого файла провайдера — `experimental_spawnPortableProcess`.

**Кто поставляет.** `provider-claude-code`, `provider-codex` (его `plugins/provider-codex/src/bridge/bridge.ts` — «the largest worked example»), `provider-pi`, `provider-acp` (собственного моста нет: он реэкспортирует набор ACP) и `examples/plugins/echo-provider` («the smallest»).

Справка: `docs/provider-bridge-protocol.md` · `docs/provider-plugin-api.md`.

## Агенты и диалекты ACP

Пять зарегистрированных диалектов, пять агентов в поставке.

| provider id | displayName | launch spec |
|---|---|---|
| `acp-cursor` | Cursor | `cursor-agent acp` |
| `acp-opencode` | opencode | `opencode acp` |
| `acp-omp` | omp | `omp acp` |
| `acp-grok` | Grok Build | `grok agent stdio` |
| `acp-hermes-agent` | Hermes Agent | `hermes acp` |

Мост поставляет пять диалектов: `acp` (общий), `cursor`, `grok`, `omp` и `opencode`. В собственной документации SDK теперь названы все пять.
{/* permalink: provider-bridge-acp.ts */}

Выбор происходит в два этапа: приоритет у явного `acpDialect` в опциях моста при регистрации; иначе `basename(launch.command)` сопоставляется с `DIALECT_IDS_BY_COMMAND`, а всё неизвестное откатывается к общему диалекту. Пользовательские агенты берутся из настройки `customAgents`, которую также заполняет официальный реестр ACP (`bb acp add <agent-id>`); они получают префикс `acp-` и значок `"Toolbox"`, а все регистрации ACP делят одно семейство. Плагин добавляет собственный диалект через `experimental_registerAcpDialect({ id, … })`, вызывая его при загрузке модуля в артефакте `bb.host`, который реэкспортирует мост; встроенный id заменить нельзя, реестр существует в одном экземпляре на хостовый артефакт, а хуки диалекта не имеют версий.

## Режим записи моста

Диагностика провайдера без гаданий.

```
BB_PROVIDER_BRIDGE_RECORD_DIR=<dir>
// every bridge process mirrors BOTH boundaries into
// <dir>/<providerId>/<threadId>/<direction>.ndjson — four directions,
// one line of { ts, run, seq, dir, line } each, with seq a single counter across all tracks.
// A bridge that spawns a CLI calls experimental_recordProviderChildIo(child, { threadId })
// right after spawn(); one whose pipe belongs to the SDK checks
// experimental_isProviderBridgeRecording() and takes the spawn over itself.
// "A recording is never rewritten": a deliberate bridge change writes
// bridge→runtime.current.ndjson beside the recorded lane.
```
