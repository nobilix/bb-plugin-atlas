Плагин — это npm-пакет с не более чем тремя точками входа, по одной на каждый процесс bb. Server entry обязательна и исполняется внутри сервера; опциональная app entry исполняется в окне приложения, а опциональная host entry — на машине, где работает агент. Общей памяти у точек входа нет. Они общаются через RPC, realtime-канал push-уведомлений и host RPC, а всё долговечное состояние живёт при server entry. bb загружает каждую точку входа с полным доверием. Если три процесса вам незнакомы, сначала прочитайте [Как устроен bb](/ru/concepts/).

## Три точки входа

Манифест — собственный `package.json` плагина. Его блок `bb` называет точки входа:

```jsonc
"bb": {
  "name": "Hello",
  "server": "./server.ts",   // required
  "app": "./app.tsx",        // optional: UI in the app window
  "host": "./host.ts"        // optional: code on the agent's machine
}
```

| Точка входа | Где исполняется | Для чего | Форма |
|---|---|---|---|
| server entry, `bb.server` | процесс сервера bb | хранилище, RPC и HTTP-маршруты, CLI-команды, инструменты агента, провайдеры, расписания | фабрика `(bb: BbPluginApi) => …`, экспортированная по умолчанию |
| app entry, `bb.app` | окно приложения, в том же JS-realm, что и собственный UI bb | панели, контролы и рендереры в окне, дополнения композера, команды палитры | `definePluginApp((app) => …)` |
| host entry, `bb.host` | процесс-воркер, который host daemon запускает на своей машине | файлы, процессы и bridge агента на машине, где работает агент | `experimental_defineHostEntry({ contract, handlers })` |

Server entry обязательна, даже если плагин только добавляет UI: `plugins/scheduled-send/server.ts` — намеренная заглушка. Все поля манифеста описаны в [Анатомии пакета](/ru/package/).
{/* permalink: pluginManifestSchema */}

Ни server entry, ни app entry не крутят главный цикл. Server entry — функция, которую bb вызывает один раз на каждую загрузку, передавая ей свежий объект `bb`. Функция регистрирует то, что даёт плагин (RPC-метод, CLI-команду, настройку, инструмент агента), и возвращает управление. App entry делает то же через `app`: регистрирует панель, компонент слота или команду, а bb монтирует компонент туда, где этот слот находится в окне. Дальше bb вызывает код плагина, когда он нужен человеку, агенту или другому процессу. Вызовы регистрации перечислены в [Namespace'ах бэкенда](/ru/backend/) и [Слотах фронтенда](/ru/frontend/).

## Как общаются точки входа

{/* DiagramBoard: canonical-data-flow */}

Server entry — центр. Любой другой вызывающий добирается до плагина через неё, и у каждого вызывающего один канал:

| Канал | Откуда → куда | Для чего | Справочник |
|---|---|---|---|
| RPC | app entry → server entry | чтение и изменение данных из UI; контракт определяется один раз в server entry, а app entry импортирует только его тип | [`bb.rpc`](/ru/backend/rpc/) |
| realtime | server entry → каждое открытое окно | сообщить страницам, что данные изменились и их надо запросить заново; ничего не хранится и не воспроизводится повторно | [`bb.realtime`](/ru/backend/realtime/) |
| CLI | CLI `bb` → server entry | команда `bb <command>` для людей и для агента; команда исполняется на сервере, а не в CLI | [`bb.cli`](/ru/backend/cli/) |
| инструмент агента | агент → server entry | нативный инструмент в сессии агента, вызывается внутри процесса сервера | [`bb.agents`](/ru/backend/agents/) |
| HTTP | внешний сервис → server entry | webhook'и и другие вызывающие извне bb | [`bb.http`](/ru/backend/http/) |
| host RPC | server entry ⇄ host entry | работа на машине агента, с сигналами в обратную сторону | [`bb.hosts`](/ru/backend/hosts/) |

Двух каналов нет намеренно. App entry не может вызвать host entry: она вызывает server entry по RPC, а server entry вызывает host entry. И ни одна точка входа не может обратиться к другому плагину напрямую.
{/* permalink: plugin-host-rpc.ts */}

Для агента картину дополняет skill. Плагин поставляет `skills/<name>/SKILL.md`, bb внедряет его в thread'ы агента, и skill говорит агенту, какую команду `bb` запустить. Дальше агент идёт через канал CLI так же, как человек, вместо того чтобы трогать хранилище плагина. Страница [Первый плагин](/ru/start/) разбирает скаффолд, который использует RPC, realtime, CLI и skill поверх одного хранилища.

## Состояние живёт при server entry

Server entry владеет всем долговечным состоянием: значениями в `bb.storage.kv`, собственной базой SQLite из `bb.storage.database()` и настройками, объявленными через `bb.settings.define`. App entry держит только то, что рендерит. Она запрашивает данные по RPC и запрашивает их заново, когда приходит realtime-сигнал, поэтому каждое открытое окно показывает одни и те же данные. Host entry хранит свои файлы на своей машине, в каталоге, который ей выдаёт bb.

Поэтому плагин остаётся небольшим по мере роста. Страница, CLI-команда и инструмент агента — три клиента одних и тех же функций в server entry, так что новая поверхность в готовом плагине обычно означает ещё один вызов уже существующего кода.

## Загрузка, reload и dispose

bb запускает фабрику server entry при каждой загрузке плагина: при старте сервера, после установки, по `bb plugin reload` и после каждого сохранения, пока следит `bb plugin dev`. Отсюда четыре правила:

1. У фабрики тайм-бокс 30 секунд. Работа, которая длится дольше или бесконечно, должна идти в фоновом сервисе, зарегистрированном через `bb.background.service`.
2. Объект `bb` действителен в пределах одной загрузки. После reload ссылка, сохранённая с предыдущей загрузки, бросает `PluginContextStaleError`, поэтому `bb` никогда не кладут в переменную уровня модуля.
3. Reload сначала загружает новый экземпляр и только потом выполняет dispose старого. Если новая фабрика бросает исключение, старый экземпляр продолжает работать, а его статус остаётся `running` с деталью «reload failed: …».
4. Уборка идёт в `bb.onDispose`. Хуки выполняются в порядке, обратном регистрации, когда плагин перезагружается или отключается или когда сервер останавливается.

В окне приложения bb заново выполняет setup app entry при каждом изменении бандла. Компонент слота, бросивший исключение, ловит собственная error boundary: bb показывает fallback, остальное окно продолжает работать, а слот остаётся отключённым до reload плагина. Точные шаги загрузки и dispose, восемь статусов и цикл горячей перезагрузки описаны на странице [Рантайм и жизненный цикл](/ru/runtime/).

## Полное доверие

bb не помещает плагины в песочницу. Server entry исполняется внутри процесса сервера с неограниченным доступом к `fs`, `net`, `child_process` и `fetch`; app entry — код страницы в том же origin, в собственном окне bb; host entry работает от того же пользователя ОС, что и агент. Граница безопасности — решение установить плагин. [Модель доверия](/ru/trust/) перечисляет, до чего может добраться код плагина, и правила дизайна, которые из этого следуют.
