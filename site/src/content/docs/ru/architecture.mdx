Плагин — это npm-пакет максимум с тремя точками входа, по одной на каждый процесс bb. Серверная точка входа обязательна и выполняется внутри сервера; опциональная клиентская работает в окне приложения, а опциональная хостовая — на машине, где запущен агент. Точки входа не разделяют память. Они общаются через RPC, пуш-канал realtime и хостовый RPC, а всё долговременное состояние хранит серверная точка входа. bb загружает каждую точку входа с полным доверием. Если вы ещё не знакомы с этими тремя процессами, сначала прочтите [Как работает bb](/ru/concepts/).

## Три точки входа

Манифест — это собственный `package.json` плагина. Точки входа перечисляются в блоке `bb`:

```jsonc
"bb": {
  "name": "Hello",
  "server": "./server.ts",   // required
  "app": "./app.tsx",        // optional: UI in the app window
  "host": "./host.ts"        // optional: code on the agent's machine
}
```

| Точка входа | Где выполняется | Для чего нужна | Форма записи |
|---|---|---|---|
| серверная точка входа, `bb.server` | процесс сервера bb | хранилище, маршруты RPC и HTTP, команды CLI, инструменты агента, провайдеры, расписания | экспортируемая по умолчанию фабрика `(bb: BbPluginApi) => …` |
| клиентская точка входа, `bb.app` | окно приложения, в том же JS-реалме, что и интерфейс bb | панели, элементы управления и рендереры в окне, дополнения к композеру, команды палитры | `definePluginApp((app) => …)` |
| хостовая точка входа, `bb.host` | процесс воркера, запускаемый демоном хоста на своей машине | файлы, процессы и мост агента на машине, где работает агент | `experimental_defineHostEntry({ contract, handlers })` |

Серверная точка входа обязательна, даже если плагин добавляет только интерфейс: `plugins/scheduled-send/server.ts` — намеренная заглушка. Все поля манифеста подробно разобраны в разделе [Анатомия пакета](/ru/package/).
{/* permalink: pluginManifestSchema */}

Ни у серверной, ни у клиентской точки входа нет главного цикла событий. Серверная точка входа — это функция, которую bb вызывает один раз при каждой загрузке и передаёт в неё свежий объект `bb`. Функция регистрирует всё, что предоставляет плагин (метод RPC, команду CLI, настройку, инструмент агента), и завершает работу. Клиентская точка входа делает то же самое через `app`: регистрирует панель, компонент слота или команду, а bb монтирует компонент на место этого слота в окне. Дальше bb вызывает код плагина, только когда он нужен пользователю, агенту или другому процессу. Все вызовы регистрации перечислены в [Бэкенд-неймспейсах](/ru/backend/) и [Слотах фронтенда](/ru/frontend/).

## Как общаются точки входа

{/* DiagramBoard: canonical-data-flow */}

Серверная точка входа служит хабом: любые другие вызывающие обращаются к плагину через неё, и у каждого вызывающего свой канал:

| Канал | Откуда → куда | Для чего нужен | Справочник |
|---|---|---|---|
| RPC | клиентская точка входа → серверная точка входа | чтение и изменение данных из интерфейса; контракт объявляется один раз в серверной точке входа, а клиентская импортирует только его тип | [`bb.rpc`](/ru/backend/rpc/) |
| realtime | серверная точка входа → каждое открытое окно | оповещение страниц об изменении данных, чтобы они запросили их заново; ничего не сохраняется и не воспроизводится | [`bb.realtime`](/ru/backend/realtime/) |
| CLI | интерфейс командной строки `bb` → серверная точка входа | команда `bb <command>` для людей и агента; команда выполняется на сервере, а не в самом CLI | [`bb.cli`](/ru/backend/cli/) |
| инструмент агента | агент → серверная точка входа | нативный инструмент в сессии агента, вызываемый внутри процесса сервера | [`bb.agents`](/ru/backend/agents/) |
| HTTP | внешний сервис → серверная точка входа | вебхуки и любые сторонние вызывающие сервисы вне bb | [`bb.http`](/ru/backend/http/) |
| хостовый RPC | серверная точка входа ⇄ хостовая точка входа | работа на машине агента с обратной отправкой сигналов | [`bb.hosts`](/ru/backend/hosts/) |

Двух каналов нет намеренно. Клиентская точка входа не может вызвать хостовую: она вызывает серверную точку входа по RPC, а та уже обращается к хостовой. Кроме того, ни одна точка входа не обращается к чужому плагину напрямую: серверная точка входа вызывает другой плагин только через его методы RPC с помощью `bb.sdk.plugins.callRpc`, а обработчик узнаёт автора вызова из `experimental_caller`.
{/* permalink: plugin-host-rpc.ts */}

Картину для агента дополняет скилл. Плагин поставляет файл `skills/<name>/SKILL.md`, bb внедряет его в треды агента, а скилл объясняет агенту, какую команду `bb` нужно запустить. Дальше агент обращается через CLI точно так же, как человек, не трогая хранилище плагина напрямую. В руководстве [Первый плагин](/ru/start/) пошагово разобран шаблон плагина, где RPC, realtime, CLI и скилл работают поверх одного хранилища.

## Состояние хранится в серверной точке входа

Серверная точка входа хранит всё долговременное состояние: значения в `bb.storage.kv`, собственную базу данных SQLite из `bb.storage.database()` и настройки, объявленные через `bb.settings.define`. Клиентская точка входа держит в памяти только то, что отображает на экране. Она запрашивает данные по RPC и перезапрашивает их при получении realtime-сигнала, поэтому во всех открытых окнах отображаются одни и те же данные. Экспериментальное чтение с тегами берёт повторные запросы на себя: `experimental_useRpcQuery` читает данные через кеш запросов bb, а серверная точка входа вызывает `bb.rpc.experimental_invalidate(tags)` там, где данные меняются. Хостовая точка входа хранит свои файлы на своей машине, в каталоге, который выделяет bb.

Именно такой подход не даёт плагину разрастаться по мере развития. Страница, команда CLI и инструмент агента — три клиента одних и тех же функций в серверной точке входа, поэтому добавление новой поверхности к готовому плагину обычно сводится к ещё одному вызову уже существующего кода.

## Загрузка, перезагрузка и dispose

bb запускает фабрику серверной точки входа при каждой загрузке плагина: при старте сервера, после установки, по команде `bb plugin reload` и после каждого сохранения, когда работает наблюдатель `bb plugin dev`. Из этого следуют четыре правила:

1. На работу фабрики отведено не более 30 секунд. Задачи, которые длятся дольше или выполняются непрерывно, выносите в фоновые сервисы, зарегистрированные через `bb.background.service`.
2. Объект `bb` действует только во время одной загрузки. После перезагрузки ссылка, сохранённая от предыдущей загрузки, выбрасывает `PluginContextStaleError`, поэтому никогда не сохраняйте `bb` в переменную уровня модуля.
3. При перезагрузке сначала загружается новый экземпляр и только потом вызывается dispose для старого. Если новая загрузка завершится ошибкой — выбросит ли исключение фабрика или сорвётся более ранний шаг вроде проверки манифеста, — старый экземпляр продолжит работать, а его статус останется `running` с уточнением «reload failed: …».
4. Очистку ресурсов описывайте в `bb.onDispose`. Эти хуки выполняются в порядке, обратном порядку регистрации, когда плагин перезагружается, отключается или когда останавливается сервер.

В окне приложения bb запускает клиентскую точку входа заново при каждом изменении бандла. Исключение внутри компонента слота перехватывает собственный error boundary: bb показывает запасной интерфейс, остальная часть окна продолжает работать, а слот остаётся отключённым до перезагрузки плагина. Точные шаги загрузки и dispose, восемь статусов и цикл горячей перезагрузки описаны в разделе [Рантайм и жизненный цикл](/ru/runtime/).

## Полное доверие

bb не изолирует плагины в песочнице. Серверная точка входа выполняется внутри процесса сервера с неограниченным доступом к `fs`, `net`, `child_process` и `fetch`; клиентская точка входа работает как код того же источника (same-origin) в собственном окне bb; хостовая точка входа выполняется от имени того же пользователя ОС, что и агент. Граница безопасности здесь — само решение установить плагин. В разделе [Модель доверия](/ru/trust/) перечислено, к чему может получить доступ код плагина, и сформулированы вытекающие из этого правила проектирования.
