Здесь подробно описано, что bb делает с плагином во время работы: где и как запускается каждая точка входа, восемь возможных статусов, порядок загрузки и выгрузки (dispose), горячая перезагрузка, сервисы и расписания. Перед чтением загляните на страницу [Как работает плагин](/ru/architecture/) — там описана базовая архитектурная модель.

## Где выполняется каждая точка входа

Четыре процесса разделены двумя контрактами: `@bb/server-contract` между клиентами и сервером и `@bb/host-daemon-contract` между сервером и демонами. Каждая точка входа плагина выполняется в отдельном процессе со своим уровнем доверия.
{/* permalink: system-overview.md */}

{/* DiagramBoard: runtime-topology */}

Браузер (или процесс рендерера в Electron) — это единый JS realm и один origin, общий для пользователя и агента. Файл плагина `dist/app.js` импортируется нативно прямо в этот realm, который не изолирован в песочнице, а шимы подтягивает из объекта `globalThis.__bbPluginRuntime`, установленного функцией `installPluginRuntime()`. CLI bb и агент обращаются к серверу через `$BB_CLI`, а также через инструменты и скиллы агента; набор инструментов фиксируется на старте сессии.

Серверный процесс — это Node со SQLite как единым источником истины, который по умолчанию слушает адрес `127.0.0.1`. Hono отдаёт маршруты `/api/v1/*` под защитой origin guard и `/internal/*` под bearer-токеном демона: `/plugins/<id>/{assets, rpc, http, cli, token}`, `/plugin-app-assets/<hash16>/`, сокет `WebSocket /ws` и `POST /plugins/reload`. Файл плагина `server.ts` собирается через esbuild и загружается прямо в этот же процесс вызовом `require` или нативным `import()`, при полном доверии (`fs`, `net`, `child_process`, `fetch`). Сервис `PluginService` управляет вызовами `loadAll` / `loadOne` / `reload`, восемью статусами, мапой `wireLookup(loaded)` и значением `generation = randomUUID()` для каждой загрузки артефакта.

На каждой зарегистрированной машине запускается один демон хоста. Он порождает дочерний процесс хост-воркера плагина из файла `dist/host.js` (`fork(bb-plugin-host-worker.mjs)`, stdio `ignore, ignore, pipe, ipc`, проверка sha256 перед запуском, не более 256 MiB) и подпроцесс провайдера, в котором работает агент. Связь с провайдером идёт по JSON-RPC 2.0 через stdio, а сборщик дельт остаётся внутри демона (`claude-code`, `codex`, `pi`, `acp-*`). К удалённой машине от провайдера машин обращаются через `MachineExecutor.exec(argv)`: плагин сам управляет транспортом, stdin остаётся закрытым, а вывод поступает через `onOutput` в лог выполнения. На такой машине запускается собственный установленный демон хоста, который регистрируется на сервере, держит собственную сессию WebSocket и запускает локальные копии хост-воркеров плагинов.

### Механизмы загрузки

| Точка входа | Обязательна | Процесс | Механизм загрузки |
|---|---|---|---|
| `bb.server` | да | серверный процесс bb, in-process | при установке из локального пути: собирается esbuild в кэшированный `server.cjs` по пути `<dataDir>/plugins/runtime/server/` и загружается через `require`; при установке из git или npm: запускается нативным `import()` из `dist/server.js`, если сборка собрана под текущий SDK, иначе пересобирается из исходников; SDK и `better-sqlite3` берутся из хостовых копий |
| `bb.app` | нет | тот же JS realm, что и у React-приложения bb | нативный `import(url)` по HTTP; шимы берутся из одного глобального объекта |
| `bb.host` | нет, ровно одна | форкнутый дочерний процесс демона хоста | `fork()` + `import(pathToFileURL(...))`, с проверкой дайджеста sha256 перед запуском |

Файлы сборок, из которых загружаются точки входа, перечислены в разделе [Анатомия пакета](/ru/package/).

{/* permalink: plugin-runtime.ts */}
{/* permalink: plugin-frontend.ts */}
{/* permalink: plugin-host-manager.ts */}

У серверной точки входа нет ни песочницы, ни изоляции. В коде `apps/server/src/services/plugins/` нет ни `worker_threads`, ни `node:vm`, ни spawn. Единственный хук загрузчика модулей, `registerHooks`, подменяет пути к SDK, `better-sqlite3` и zod на хостовые копии и добавляет маркер перезагрузки: никаких белых списков модулей и перехвата импортов нет. Нативные аддоны не поддерживаются, а сама ошибка `ERR_DLOPEN_FAILED` снабжается соответствующим пояснением.

Клиентская точка входа делит realm с приложением, но оборачивается в собственный error boundary. Конструкции `eval`, `new Function` и blob-ссылки не используются. Бандл загружается по контентно-адресуемому пути `/api/v1/plugin-app-assets/<hash16>/app.js`, который отдаётся как неизменяемый (immutable), а его экспорт по умолчанию должен содержать метку `__bbPluginApp === true`. Каждая регистрация оборачивается в `PluginSlotBoundary`: слот, завершившийся ошибкой, остаётся отключённым до конца сессии или до перезагрузки плагина.
{/* permalink: PluginSlotBoundary */}

Хостовая точка входа доставляется по контентному адресу. Демон скачивает артефакт через внутренний API (`GET /internal/plugins/<id>/host/<sha256>`), проверяя размер и хэш как при скачивании, так и при каждом чтении из кэша. Демон сохраняет артефакт по пути `<daemonDataDir>/plugin-host-artifacts/<id>/<sha256>/host.mjs`.
{/* permalink: node-artifact-cache.ts */}

### Три точки входа рядом друг с другом

| | `server.ts` | `app.tsx` | `host.ts` |
|---|---|---|---|
| Процесс | серверный процесс bb | JS realm приложения (браузер или рендерер) | форкнутый дочерний процесс демона хоста |
| Форма модуля | `export default (bb: BbPluginApi) => …`, синхронный или асинхронный; возвращаемое значение игнорируется | `export default definePluginApp((app) => …)`, с меткой `__bbPluginApp` | `export default experimental_defineHostEntry({ contract, handlers, dispose? })` |
| Доверие | полное: тот же процесс, что и у сервера; никакой изоляции | код страницы в том же origin с полным доверием, не песочница; изолирован только от сбоев |
| Что разрешено импортировать | любые встроенные модули Node и зависимости npm; SDK и `better-sqlite3` берутся из хоста | всё, что работает в браузере; шимированные пакеты берутся из хоста; `zod` бандлится внутрь или берётся из версионированного слота хоста при сборке силами bb | чистый JS бандлится целиком; закрытый пакет `@bb/*` запрещён на этапе резолва и загрузки |
| target / format | esm · node · node22 · sourcemap · minify (кэшированная сборка при установке из пути — cjs) | esm · browser · es2022 · minify (без минификации в dev) | esm · node · node22 · sourcemap · minify · без externals |
| Как общается с остальными | отдаёт `bb.rpc`/`bb.http`, публикует `bb.realtime`, вызывает хост через `bb.hosts.experimental_client` | `useRpc()` → POST; `useRealtime()` ← WebSocket; не может напрямую вызывать хост | отвечает на `plugin.host.call`, отправляет `experimental_emitSignal` обратно на сервер |
| Типы | `import type { BbPluginApi } from "@get-bb/plugin-sdk"`, стираются при загрузке | `@get-bb/plugin-sdk/app` | `@get-bb/plugin-sdk/host` |

## Состояния объектов

Плагин считывает эти состояния через `bb.sdk` и реагирует на них с помощью событий треда.

| Объект | Состояния |
|---|---|
| Тред | `pending`, `idle`, `starting`, `active`, `stopping`, `error` |
| Ход | `accepted` → `dispatched` → `started` → `completed`\|`failed`\|`interrupted` |
| Окружение | `creating`, `provisioning`, `ready`, `error`, `destroyed` |
| Машина | `available` \| `setup-required` \| `unavailable` |

Повтор запрашивается по ссылке (`bb.sdk.threads.retry`), а не повторной отправкой сообщения. Переходы состояний окружения показаны в разделе [Провайдеры окружений](/ru/advanced/environments/).

## Детали протокола

### Контракт RPC

```ts
// server.ts
import { defineRpcContract } from "@get-bb/plugin-sdk";
import { z } from "zod";

export const rpcContract = defineRpcContract({
  listIssues: { input: z.object({ filter: z.string() }),
                output: z.object({ issues: z.array(z.string()) }) },
  ping: { input: z.null(), output: z.object({ ok: z.literal(true) }) },
});

export default function plugin(bb: BbPluginApi) {
  bb.rpc.register(rpcContract, {
    listIssues: ({ filter }) => ({ issues: search(filter) }),
    ping: () => ({ ok: true as const }),
  });
}
```

Валидатором служит Standard Schema v1, которую напрямую реализует zod 4. Значение `z.null()` во входных данных позволяет фронтенду опускать аргумент при вызове. Имена методов состоят из разделённых точками сегментов из букв, цифр, `-` и `_`. Вызов `useRpc<typeof rpcContract>()` отправляет запрос `POST /plugins/<id>/rpc/<method>` с заголовками `auth: local` (origin guard) и `no-store`: сначала отрабатывает входная схема, затем обработчик, затем выходная схема. Неизвестные методы возвращают `404 unknown_method`, невалидный ввод — `400 invalid_input`. Вторым аргументом каждый обработчик получает контекст: `experimental_caller` принимает вид `{ kind: "plugin", pluginId }`, если вызов пришёл от другого плагина через `bb.sdk.plugins.callRpc`, и `{ kind: "client" }` во всех остальных случаях. Параметр `invalidates` на уровне контракта упразднён: серверная точка входа обновляет открытые чтения методами `bb.rpc.experimental_invalidate(tags)` или `experimental_invalidateAll()` прямо в тех местах, где меняются данные.

### Маршруты HTTP и токен

```ts
// mount: /api/v1/plugins/<id>/http<path> — an EXACT match;
// ":" and "*" are literal characters, not parameters and not wildcards
bb.http.route("POST", "/upload", async (context) => {
  const body = await readRequestBody(context.req.raw);
  return context.json({ ok: true }, 201);
}, { auth: "token" });

bb.http.experimental_websocket("/live", ({ request, url }) => ({
  onOpen(socket) { socket.send("hello"); },
  onMessage(socket, data) { /* … */ },
  onClose({ code, reason }) { /* reload/disable → 1012 */ },
}), { auth: "local" });
```

Команда `bb plugin token <id> [--rotate]` генерирует 32 случайных байта в шестнадцатеричном виде и сохраняет в `<dataDir>/plugins/<id>/secrets/.http-token` с правами `0o600`; значения сравниваются через `timingSafeEqual`. Токен действует строго на один плагин и только на его маршруты с опцией `auth: "token"`: он не заменяет пользовательскую сессию и не удостоверяет личность.
{/* permalink: bb plugin token */}

:::caution[Глобальный origin guard и его единственное исключение]
Все маршруты под `/api/v1/*` проходят через `browserRequestProblem`, кроме `/api/v1/plugins/<id>/http/*`, который шаблон `PLUGIN_WIRE_HTTP_PATH` исключает из проверки, чтобы маршруты с `auth: "token"` и `auth: "none"` вообще могли работать. Это защита от CSRF и проверка источника, а **не аутентификация**: локальный клиент не из браузера без заголовка `Origin` спокойно её проходит. Пути `/internal/*` требуют bearer-токен демона, и именно там отдаётся скачивание артефакта хоста.
{/* permalink: PLUGIN_WIRE_HTTP_PATH */}
:::

### Realtime

Вызов `bb.realtime.publish(channel, payload)` передаёт данные по цепочке `notifyPluginSignal` → `broadcastToAllClients` и уходит каждому клиенту через общий сокет `WebSocket /ws` в виде `{ type, pluginId, channel, payload }`. В первой версии протокола серверных подписок на каналы нет: хук `useRealtime(channel, handler)` фильтрует события по `pluginId` и `channel` уже на стороне клиента. Полезная нагрузка попадает в сокет каждого подключённого клиента, поэтому **конфиденциальности этот канал не гарантирует**. Сигналы повторно не воспроизводятся, поэтому долговременное состояние нужно проверять заново при каждом переходе `useRealtimeConnectionState()` в статус `connected`.
{/* permalink: notifyPluginSignal */}

### CLI, инструменты агента и хостовый RPC

Команда вида `bb <command> …` отправляет запрос `{ argv, cwd?, threadId? }` на адрес `POST /plugins/<id>/cli`; массив argv имя самой команды не включает. Инструмент агента вызывается внутри серверного процесса с контекстом `ctx: { threadId, projectId, signal }` и возвращает ошибку текстом, а не исключением.

Сервер обращается к хостовой точке входа через `bb.hosts.experimental_client({ contract }).call(method, input, { hostId, signal, timeoutMs })`. На уровне протокола вызовы идут как `plugin.host.call` / `.cancel` / `.dispose` через WebSocket демона. В обратную сторону вызов `context.experimental_emitSignal(name, payload)` приходит в обработчик `experimental_onSignal`. Простаивающий воркер выгружается через 5 минут. Ограничения на размер вывода, полезной нагрузки и таймауты для CLI и хостового RPC приведены в таблице числовых лимитов на странице [Серверные неймспейсы](/ru/backend/).
{/* permalink: plugin-host-rpc.ts */}

## Статусы

```ts
// packages/server-contract/src/api/plugins.ts
export const pluginRuntimeStatusSchema = z.enum([
  "starting", "running", "error", "incompatible",
  "missing", "disabled", "degraded", "needs-configuration",
]);
// there is NO "healthy" value — the healthy state is called "running"
```

| Статус | Причина |
|---|---|
| `starting` | запись включена, но плагин ещё не загружен |
| `disabled` | `!row.enabled`, для источника действует блокировка загрузки или включён безопасный режим плагинов |
| `missing` | вызов `stat(row.rootDir)` вернул ошибку → «plugin directory not found: … (reinstall)» |
| `error` | манифест не парсится; ошибка артефакта хоста; фабрика выбросила исключение или не уложилась в лимит времени; сервис завершился ошибкой во время активации |
| `incompatible` | не подошли требования `engines.bb` или `engines.bbPluginSdk`; проблема с артефактом плагина из дистрибутива bb |
| `needs-configuration` | плагин вызвал `bb.status.needsConfiguration(msg)` либо сервис завершился с ошибкой `NeedsConfigurationError` |
| `degraded` | фоновый сервис не успел остановиться за время `serviceStopTimeoutMs` (5 с); плагин не будет загружаться повторно, пока сервис не остановится |
| `running` | успешная загрузка, а также статус, сохраняемый при ошибке любого шага перезагрузки (с деталью «reload failed: …») |

{/* permalink: pluginRuntimeStatusSchema */}

Ошибка `NeedsConfigurationError` сопоставляется по имени, поэтому импортировать класс из рантайма не нужно: достаточно вызвать `throw Object.assign(new Error(msg), { name: "NeedsConfigurationError" })`. Статус сбрасывается при следующей загрузке. Соседние перечисления: состояние сервиса принимает значения `"running" | "backoff" | "stopped"`, статус расписания `lastStatus` — `"running" | "ok" | "error"`, а результат обновления — `"current" | "update-available" | "pinned" | "incompatible" | "unavailable"`.

## Порядок загрузки и dispose

При перезагрузке сначала загружается новый экземпляр, и только затем выгружается старый. Если новая фабрика выбросит ошибку или упадёт один из предыдущих шагов, старый экземпляр продолжит работать: вызов dispose находится внутри `loadOne` строго после вызова фабрики.

{/* DiagramBoard: lifecycle-order */}

Шаги `loadOne` по порядку:

| # | Шаг | Примечание |
|---|---|---|
| 1 | блокировка → safe mode → identity → enabled | заблокированный источник, безопасный режим или `!row.enabled` → `disabled`; если сервис прошлого экземпляра всё ещё работает → `degraded` |
| 2 | `stat(rootDir)` → манифест | каталога нет → `missing` |
| 3 | `engines`, диапазон версий SDK, артефакты плагинов из поставки | нет совпадения → `incompatible` |
| 4 | клиентский бандл и хостовый артефакт | дайджест проверяется по файлу `host.meta.json` |
| 5 | ассеты айдентики (брендинг) | валидатор SVG может прервать загрузку ошибкой |
| 6 | `createPluginApi` | объект `bb` под эту загрузку |
| 7 | сборка или импорт серверной точки входа + фабрика | жёсткий лимит времени в 30 с |
| 8 | dispose предыдущего экземпляра | только здесь: строго после фабрики; если один из его сервисов зависнет, новый экземпляр тоже будет отклонён |
| 9 | `loaded.set(id, …)` | плагин становится виден для `wireLookup` |
| 10 | `handle.activate()` | провайдеры, AI-сервисы, порты |
| 11 | cron-строки и сервисы | переход в статус → `setStatus("running")` |

Функция `disposePluginInstance` выполняется в строго определённом порядке:

| # | Шаг | Примечание |
|---|---|---|
| 1 | `closeWebSockets` | с кодом закрытия 1012 |
| 2 | `disposePluginHost` | передаётся `{ pluginId, generation }` |
| 3 | `abortPluginToolCalls` | с причиной `"plugin-disposed"` |
| 4 | `interruptInteractions` | с причиной `reason: plugin-disposed` |
| 5 | `stopServices` | даётся 5 с → иначе переход в `degraded` |
| 6 | `waitForWebSocketsClosed` | ожидание до 5 с |
| 7 | `onDispose` | по принципу LIFO; ошибка в одном хуке не прерывает остальные |
| 8 | `drainInvocations` | ожидание завершения текущей работы до 5 с, затем освобождение вызывающих сторон |
| 9 | закрытие `better-sqlite3` | закрываются все отслеживаемые дескрипторы |
| 10 | `finally handle.invalidate()` | любые последующие вызовы `bb.*` вызовут `PluginContextStaleError` |

Сбой одного хука dispose не останавливает остальную очистку. Функция `disposeOne` дополнительно освобождает модульные корни плагина, удаляет артефакт хоста и отзывает зарегистрированные общие порты.

На выполнение фабрики отводится не более 30 с: лимит `DEFAULT_LOAD_TIMEOUT_MS = 30_000` задаётся через `runFactoryTimeBoxed`. Регистрации по ключам за один вызов фабрики должны быть уникальными: настройки, маршруты, методы RPC, сервисы, расписания, команды CLI, инструменты, а также провайдеры инструкций и упоминаний. Слушатели событий (`bb.events.on`, `settings.onChange`, `bb.onDispose`) работают аддитивно.

Хуки `onDispose` выполняются в порядке, обратном порядку их регистрации: именно в них нужно очищать таймеры и закрывать соединения. После вызова `handle.invalidate()` любой метод сохранённого объекта `bb` выбрасывает исключение `PluginContextStaleError`, поэтому сохранять `bb` в переменных уровня модуля нельзя.
{/* permalink: PluginContextStaleError */}

Маршруты HTTP и WebSocket, методы RPC, инструменты агента, хуки, провайдеры упоминаний, провайдеры окружений и машин, а также расписания нельзя разрегистрировать по отдельности. Они привязаны к дескриптору и становятся недоступными в момент изменения `loaded`, поскольку все вызовы идут через `wireLookup`, читающий только эту мапу. Строки cron остаются в таблице `plugin_schedules`, но фоновый планировщик пропускает записи, плагинов которых нет в `loaded`.

При неудачной активации откатываются три вещи. Каждая запись в `rollbackGenerations`, запущенная в обратном порядке, возвращает предыдущую эпоху модульного корня и восстанавливает вытесненные записи CommonJS; функция `discardCandidate` прерывает кандидата, останавливает его интерактивные взаимодействия, закрывает дескрипторы баз данных и инвалидирует его дескриптор; при этом старый экземпляр не разрушался. Вызывающая сторона получает ошибку вида «&lt;message&gt; (the previous instance is still running)». Управляемые обновления используют второй механизм отката: неудачная активация восстанавливает сохранённый снимок состояния, а поле `pluginApplyUpdateResultSchema.outcome` принимает значение `"rolled-back"`.

### Три значения термина «generation»

| Значение | Что означает |
|---|---|
| 1. эпоха кэша модулей (сервер) | `registerHooks` добавляет параметр `?bbPluginLoad=<rootId>.<epoch>` к каждому URL вида `file:` внутри корня плагина с изменившимся кодом и очищает записи `require.cache` для этого корня: как для корня источника `path` или `builtin`, так и для каталога файла ESM `dist/server.js`. Это заставляет рантайм полностью перевычислить граф модулей |
| 2. идентификатор артефакта хоста | строка `randomUUID()` на каждую загрузку артефакта хоста; по ней адресуется dispose воркера, а также фильтруются сигналы и события завершения процесса воркера |
| 3. поколение монтирования фронтенда | монотонный счётчик внутри каждого клиента, который растёт при каждой переинтерпретации кода и передаётся в content script как `context.generation` |

## Горячая перезагрузка: `bb plugin dev`

Оба пути используют функцию `createPluginDevLoop`: задержка debounce 300 мс с игнорированием каталогов `dist`, `node_modules`, `.git`; цикл работы выглядит как `targets()` → сборка app → сборка host → перезагрузка.
{/* permalink: createPluginDevLoop */}

- Команда `bb plugin dev [path]` отслеживает изменения через `fs.watch(rootDir, { recursive: true })` и перезагружает плагин запросом `POST /plugins/reload?id=…`. Каталог уже должен быть установлен в системе, а клиентский бандл собирается без минификации.
- Сервер следит за исходниками собственных плагинов только при установленном флаге `deps.watchBuiltinPluginSources`: пересборка происходит in-process, после чего вызываются `disposeOne` + `loadOne`. При сбое вотчера в лог пишется сообщение «source watcher failed; hot reload is off until the server restarts».
- Открытые вкладки подтягивают новый интерфейс по уведомлению `plugins-changed` через WebSocket; плагин, у которого `hash` бандла остался прежним, пропускается. Ошибки dev-сборки попадают в поле деталей статуса с префиксами `frontend bundle build failed` / `host bundle build failed`.

## Фоновые сервисы и расписания

Сервис стартует после полного завершения фабрики и обязан завершать работу при сигнале отмены `signal`. При падении он перезапускается с ограниченным экспоненциальным backoff: базовый интервал 1 с, максимум 60 с, сброс счётчика здоровья через 5 минут. Ошибка за пределами промиса `start` (необработанное событие `'error'` в EventEmitter, исключение внутри таймера, оторванный rejection) также считается падением сервиса. Контекст отслеживается через `AsyncLocalStorage`, поэтому необработанное исключение внутри плагина не роняет серверный процесс.

Расписание — это cron из 5 полей по локальному времени сервера, зафиксированный в надёжной строке таблицы `plugin_schedules` с ключом `(pluginId, name)`. Фоновый планировщик периодически забирает задачи операцией compare-and-swap по полю `next_run_at`, но делает это только пока плагин загружен. Исключение, выброшенное задачей по расписанию, сохраняется в полях `last_status`/`last_error` и отображается в выводе `bb plugin list`; статус самого плагина от этого не меняется.
