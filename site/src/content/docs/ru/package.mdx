Плагин — это обычный npm-пакет. Здесь подробно разобрано всё, из чего он состоит: манифест, правила разделения зависимостей, шаблон плагина, артефакты сборки с метаданными, логика вычисления идентификатора плагина и состояние на диске. Роль манифеста выполняет `package.json`: его верхний уровень разбирается со схемой `.passthrough()`, а секция `bb` и вложенная `bb.branding` объявлены со `.strict()`, поэтому любой неизвестный ключ внутри `bb` делает манифест невалидным.
{/* permalink: pluginManifestSchema */}

## Манифест: поля `bb.*` и `engines`

| Поле | Обяз. | За что отвечает | Подводные камни |
|---|---|---|---|
| `name` | да | npm-имя и единственный источник идентификатора плагина | по соглашению принято `bb-plugin-<x>`; пакеты с областью видимости вроде `@acme/bb-plugin-<x>` тоже подходят; идентификаторы всех плагинов из поставки зарезервированы |
| `version` | да | вшивается в артефакты | управляемая установка отклоняет `dist/*.meta.json`, если `pluginVersion` не совпадает с манифестом |
| `engines.bb` | нет | semver-диапазон версий приложения; проверяется в рантайме и при выборе обновления | сборки для разработки (`0.0.0`) не проверяются, но сообщают об этом в результате |
| `engines.bbPluginSdk` | нет | диапазон SDK; трактуется как нижняя граница, а не верхняя | если поле опущено, манифест считается устаревшим. Установка через `git:` или `npm:` отклонит плагин, если его SDK новее версии на хосте или принадлежит другой мажорной версии; при установке из path во время загрузки плагин получит статус `incompatible` |
| `bb.name` | да | понятное человеку имя для Settings, каталога и боковой панели | не путать с `name` и идентификатором плагина |
| `bb.description` | да | одно предложение: карточка во вкладке Browse и первый абзац страницы | укладывайтесь примерно в 140 символов и синхронизируйте текст с `PLUGIN_OVERVIEW.md` |
| `bb.branding` | да | айдентика плагина; строгий объект | обязательно хотя бы одно из двух полей: `icon` или `logo.light` |
| `bb.branding.icon` | одно из | имя иконки bb (`"Zap"`) или путь к SVG-файлу плагина (`"./assets/icon.svg"`) | глиф с неймспейсом `"<pluginId>/<name>"` здесь запрещён; путь к файлу плагина обязан заканчиваться на `.svg` |
| `bb.branding.logo` | нет | `{ light, dark? }`: крупный логотип для свободных мест | `.svg/.png/.webp`; `dark` без `light` вызывает ошибку; `bb plugin build` отклоняет SVG-логотипы со скриптами внутри вектора; автопоиска логотипа в корне нет |
| `bb.branding.experimental_icons` | нет | `Record<name, "./x.svg">`: собственный набор иконок плагина для строк таймлайна и значков провайдеров | имена должны соответствовать шаблону `[a-z0-9-]` и начинаться с буквы или цифры, ≤48 символов, ≤64 записей; размер файлов ≤32 KiB; валидатор SVG работает только на отказ (запрещены `script/style/iframe/foreignObject/image/a`, обработчики `on*`, href без `#`, `xml:base`); нарушение ломает загрузку плагина с указанием имени иконки |
| `bb.experimental_providers` | нет | массив объектов `{ kind: "agent", id, displayName }`: объявление провайдеров агента, регистрируемых плагином, ещё до его запуска | позволяет показывать агентов выключенного плагина в списке Settings → Providers; в рантайме никаких возможностей не даёт. Допустим только `kind: "agent"` |
| `bb.server` | да | серверная точка входа | обязательна даже для чисто интерфейсных плагинов: например, `plugins/scheduled-send/server.ts` сделан намеренной заглушкой. Для установки из path команда `bb plugin build` не нужна: bb сам бандлит TypeScript при загрузке и кэширует результат |
| `bb.app` | нет | клиентская точка входа → `dist/app.js` + `app.css` + `app.meta.json` | при установке из path и git собирается прямо на месте; npm-пакет обязан поставлять готовую папку `dist/` |
| `bb.host` | нет, одна | хостовая точка входа под полным доверием в Node 22 ESM → `dist/host.js` | вызывается из собственной серверной точки входа через типизированный host RPC; демон скачивает её лениво и проверяет дайджест |
| `bb.skills` | нет | переопределяет корни для автоимпорта скиллов | по умолчанию `skills/`; значение `[]` отключает импорт. В репозитории значение буквально задано как `["skills"]` (каталог, а не имена), кроме `plugins/plugin-api-docs`, где импорт отключён через `[]`; 17 плагинов поставляют `skills/` вообще без этого поля |
| `bb.themes` | нет | массив объектов `{ id, name, description?, css, codeTheme? }` → Settings → Appearance и `bb theme list` | выбираемый id формируется как `plugin:<plugin-id>:<id>`; темы добавляют только загруженные плагины. Ни один плагин из поставки это поле не использует |

## `dependencies` против `devDependencies`: асимметричное правило

**`dependencies`.** Всё, что импортируется во время работы и не шиммируется со стороны bb. Команда `bb plugin build` инлайнит эти зависимости; установка из git резолвит только этот список. Если пакет нужен для сборки, но остался в devDeps, плагин невозможно будет установить из git — в том числе при вызове npm из упакованного CLI, который запускается с `NODE_ENV=production`.

Пакета `zod` намеренно нет в списке шимов: слот для его неймспейса добавил бы +193 KB в несжатом виде / +33 KB brotli к полезной нагрузке загрузки хоста. Поэтому он живёт в `dependencies`. Когда bb собирает клиентский бандл самостоятельно (при установке из path или git), он берёт zod из отдельного версионированного слота (`VERSIONED_RUNTIME_SLOT_BY_SPECIFIER`), который хост подгружает, только если плагин в нём нуждается, и только если мажорная версия zod у плагина совпадает с версией хоста и не новее её; `bb plugin build` бандлит его сам.

Единственное исключение: в плагинах провайдеров `@get-bb/plugin-sdk` остаётся в `dependencies`, поскольку хостовая сборка бандлит субпуть `/provider-bridge` из локальной установки плагина.

**`devDependencies`.** Типы, инструментарий и все шиммируемые пакеты. Единственным источником правды служит `RUNTIME_SLOT_BY_SPECIFIER`. Если отправить шиммируемый пакет в `dependencies`, появится вторая копия синглтона рядом с версией хоста.
{/* permalink: RUNTIME_SLOT_BY_SPECIFIER */}

Команда `bb plugin types` повторно закрепляет SDK и devDeps, нужные только для типов, за версиями запущенного bb; `bb plugin types --check` служит проверкой в CI: она ничего не пишет на диск и завершается с ненулевым кодом при любых расхождениях.

```
// packages/plugin-build/src/runtime-shims.mjs — the full shim list
react · react-dom · react-dom/client · react/jsx-runtime · react/jsx-dev-runtime
@get-bb/plugin-sdk/app (+ legacy @bb/plugin-sdk/app)
@pierre/diffs · @pierre/diffs/react
@radix-ui/react-{alert-dialog, context-menu, dialog, dropdown-menu, hover-card,
                 menubar, navigation-menu, popover, select, tooltip}
sonner · vaul · clsx · tailwind-merge · class-variance-authority
@bb/shared-ui/icon · @bb/shared-ui/question-form-host · @bb/shared-ui/voice-input-textarea
```

В тот же файл заложены два правила допуска: (1) семантика синглтона — то есть один React, единое пространство порталов radix, вызов `toast()` должен попадать в тостер хоста, `vaul` мутирует `document.body`, а `@pierre/diffs` требует идентичности контекста; (2) библиотеки, которые иначе дублировал бы каждый плагин: `tailwind-merge ^3`, `clsx ^2`, `cva ^0.7` и `Icon` из shared-ui (~110 KB карты hugeicons на каждую копию).

## Шаблон `bb plugin new <name>`

У команды нет никаких флагов: ни `--app`, ни `--headless`, ни `--yes`. Шаблон всегда включает клиентскую часть; в README объясняется, что для создания headless-плагина нужно удалить `bb.app`, `app.tsx`, `components/`, `hooks/`, `lib/`. Каталог всегда получает имя `bb-plugin-<derived-id>`, независимо от области видимости.

```
bb-plugin-<id>/
├── package.json        # manifest: version 0.1.0, type module, engines {bb, bbPluginSdk}
├── server.ts           # server entry: a todo store on bb.storage.kv → RPC + CLI + skill
├── app.tsx             # app entry: definePluginApp + one navPanel
├── tsconfig.json       # strict, ES2022, moduleResolution bundler, paths {"@/*": ["./*"]}
├── components.json     # shadcn config; the @bb registry is pinned to the release tag of the current bb
├── .gitignore          # exactly "dist/\nnode_modules/"
├── README.md           # a long author's README
├── PLUGIN_OVERVIEW.md  # store copy: ≤4000 chars (target 700–1800), ## sections, no HTML or images
├── skills/
│   └── example-todos/SKILL.md   # agent instructions for the bb <id> command
├── components/ui/      # pre-vendored button, card, checkbox, dialog, input
│   ├── icon.tsx · motion.ts · overlay-trigger.ts · responsive-overlay.tsx · coarse-pointer-sizing.ts
│   └── hooks/ use-compact-viewport.tsx · use-media-query.ts · use-pointer-coarse.ts
├── hooks/useBrowserDimmingModal.ts
└── lib/ portal-scope.ts · utils.ts
```

:::note[Чего нет в шаблоне]
Каталог `types/` (SDK берётся из npm, и тесты проверяют его отсутствие), конфиг vitest с файлом теста, `app.css`, `dist/`. Строка из changelog 0.41 «scaffold with a test that runs» текущему шаблону не соответствует.
{/* permalink: scaffoldPlugin */}
:::

## `dist/` и `meta.json`

| Артефакт | Файлы |
|---|---|
| сервер (всегда) | `dist/server.js`, `server.js.map`, `server.meta.json` |
| клиент (если есть `bb.app`) | `dist/app.js`, `app.css`, `app.meta.json` |
| хост (если есть `bb.host`) | `dist/host.js`, `host.js.map`, `host.meta.json` |

Все три артефакта собираются через esbuild во временную папку `mkdtemp` внутри `dist/` и переименовываются на месте.

```jsonc
// packages/plugin-build/src/plugin-artifact-meta.ts
{
  "sdkMajor": <PLUGIN_SDK_MAJOR>,
  "sdkVersion": "<PLUGIN_SDK_VERSION>",
  "artifactFormatVersion": 1,
  "pluginId": "<derivePluginId(name)>",
  "pluginVersion": "<package.json version>",
  "builtWith": { "bbVersion": "…", "pluginSdkVersion": "…" }
}
// host.meta.json adds a seventh field:
// "artifactDigest": "<sha256 hex of host.js>"
// app.meta.json adds "runtimeSlots": the shimmed host modules the bundle imports
```

На принимающей стороне `validatePluginArtifactMeta` требует, чтобы `sdkMajor` совпадал с текущим `PLUGIN_SDK_MAJOR`, а `pluginId` и `pluginVersion` — с манифестом; поле `builtWith.pluginSdkVersion` должно содержать корректный semver и совпадать с `sdkVersion`. Пока `PLUGIN_SDK_MAJOR` равен 0, предварительно собранный `dist/server.js` используется только тогда, когда его `sdkVersion` совпадает с работающим SDK; в противном случае bb игнорирует его и собирает серверную точку входа заново из исходников.
{/* permalink: validatePluginArtifactMeta */}

## Определение идентификатора плагина

```
// packages/domain/src/plugin-id.ts — derivePluginId
1. if the package name is scoped, take the segment after "/"
2. strip the leading "bb-plugin-"
3. lowercase; any character outside [a-z0-9-] → "-"; trim "-" at the edges
4. an empty result throws

pluginIdSchema = /^[a-z0-9][a-z0-9-]*$/u

@acme/bb-plugin-Notes  → notes
bb-plugin-simple-notes → simple-notes   // directory plugins/docs
bb-plugin-bb--git      → bb--git        // directory plugins/git
```

{/* permalink: derivePluginId */}

Идентификатор служит неймспейсом для маршрутов, хранилища, настроек и команд CLI. Он не обязан совпадать с именем каталога: в именах пакетов у более новых плагинов из поставки используется префикс `bb--`, поэтому каталог `plugins/git` получает идентификатор `bb--git`. Команда `bb plugin new` также отклоняет зарезервированные имена встроенных команд core.

## Состояние на диске

```
<dataDir>/plugins/<id>/data.db          its own SQLite (WAL, busy_timeout 5000, incremental auto-vacuum)
<dataDir>/plugins/<id>/secrets/         secret settings, one file per key, + .http-token
<dataDir>/plugins/<id>/logs/plugin.log  JSONL, rotated into plugin.log.1 at 5 MiB
<dataDir>/plugins/git/ · npm/           managed installs
<dataDir>/plugins/snapshots/<id>/       the state copy taken before an update, for rollback
<dataDir>/plugins/runtime/server/…      cached server builds of path installs
<dataDir>/plugins/cache/git|npm/…       materialized checkouts of the sources
<dataDir>/plugins/toolchain-*           the downloaded esbuild/tailwind toolchain (cache it in CI)
<dataDir>/skills-generated/             the server-generated plugin-commands skill

<daemonDataDir>/plugins/<encoded id>/host-data                 the host side
<daemonDataDir>/plugin-host-artifacts/<encoded id>/<sha256>/host.mjs   the artifact cache
```

В упакованном приложении `dataDir` по умолчанию указывает на `~/.bb/`, а `pnpm dev` переносит его в `~/.bb-dev/<checkout-instance>/`. Именно поэтому существует `bb.server.experimental_dataDir` вместо «guess `~/.bb`».
